# MCP Server CLAUDE.md

## Purpose

TypeScript MCP (Model Context Protocol) server exposing the Proof Holdings REST API as 176 tools for AI agents. **Runs with or without a key** (`h-mcp-public-mode`): with no `PROOF_API_KEY` the bootstrap surface (`create_account`, `send_account_email`, `wait_for_account_creation`, `start_login`, `wait_for_login`), the public verification surface (`validate_proof`, `list_revoked_proofs`, `verify_delegation`, `verify_delegations`) and the local `render_auth_link` all work, and every other tool answers a structured `api_key_required` — the server no longer exits at startup, which is the precondition both the publisher showcase and the remote server depend on. Published to npm as `@proof-holdings/mcp-server` (MIT). Tool names match the `tool_name` values in `docs/api-map.yaml` exactly — the parity map is the single source of truth for interface coverage (so the full tool→endpoint listing lives there, not here).

## Narrative Summary

Follows the same HTTP client pattern as the JavaScript SDK — one `HttpClient` handles auth, retries with exponential backoff, and error normalization. Tool modules are organized by resource; each exports a `registerTools(tool, http)` that binds tool definitions (name, description, Zod schema, handler). The one exception is `render-auth-link`, which exports `registerTools(tool)` with no `http` (local QR generation only). **Two transports** (`h-mcp-remote`): stdio (`src/server.ts`, one user per process) and Streamable HTTP (`src/remote.ts`, many users per process, deployed as its own service). Both build their server through the SAME factory, `src/factory.ts` — which holds the only copy of the registration list.

## Key Files

### Application Structure
- `src/factory.ts` - `createProofServer({apiKey?, baseUrl, remote?})` → a FRESH `McpServer` + a FRESH `HttpClient` with every tool module registered. `remote` is set by the Streamable HTTP entrypoint and selects the RECIPE wherever one is stated — the `api_key_required` text, the per-tool access notice and the server `instructions` — since the stdio instruction (set `PROOF_API_KEY`, restart) is impossible on a server somebody else runs. The registrar handed to the modules is a WRAPPER over `server.tool.bind(server)` that appends `accessNoticeFor()` to each description: one place instead of 176, and the only place that knows the transport (a description literal cannot). It touches the second argument only when it is a string, so the SDK's other call shapes pass through untouched. The constructor also carries `instructions` (`serverInstructions()`), the one channel that states the whole arrangement once. The single registration list for both entrypoints; `__tests__/factory.test.ts` pins its completeness against `src/tools`, asserts `server.ts` keeps no second copy, and sweeps EVERY registration for the notice rather than sampling names.
- `src/server.ts` - stdio entry point: calls the factory once and connects `StdioServerTransport`. One user per process, so one client for the process is correct here.
- `src/authBoundary.ts` - The ONE place the line between "works with no account" and "needs one" is written (`h-mcp-oauth-remote-wiring`): `KEYLESS_TOOLS` (the ten tools of the bootstrap + public-verification + local surfaces, derived from `http.ts`'s `PUBLIC_PATHS` plus the two verifier tools and `render_auth_link`), `keyedToolsIn()` (fail-closed — an unknown name is KEYED, so a typo breaks a tool instead of opening a hole), and the refusal itself: `authorizationChallenge()` (`WWW-Authenticate: Bearer …, resource_metadata="…"`) plus `authorizationRequiredBody()`. Also holds a DELIBERATE second copy of the backend's `PROTECTED_RESOURCE_METADATA_PATH` — this package cannot import backend `src/`, so `src/__tests__/drift/mcp-oauth-remote-wiring.test.ts` compares the two as text (`soleMatch`, exactly one occurrence). Also `SESSION_TOOLS` — the tools a `start_login` session actually reaches, i.e. the ones whose endpoint path the client SIGNS with the session token (`SESSION_AUTH_PREFIXES` plus the `usesSessionAuth` exact matches in `./http.ts`). That is NOT the map's `auth` column: two `jwt+api_key` endpoints sit under those prefixes and are signed with the session too, and the refusal has to tell the caller the client's truth, not the map's. Hand-written here because the package cannot read `docs/api-map.yaml` at runtime, and held equal in BOTH directions by `validateMcpSessionToolCoverage` (`scripts/validate-api-map.ts`) and its mirror in `src/__tests__/drift/api-parity.test.ts` — which additionally compares the text parse against the module it IMPORTS, because a parse alone over-reads a name inside a block comment and under-reads a double-quoted one, and either leaves the map check green over a set the server never uses. That import is sound only while this file imports nothing, which the same case asserts. The refusal text is written for the WORST measured client rather than the best: Inspector replays the call and Desktop does after one press, but Claude Code stops before the browser step and never replays, so it must say "sign in AND call the tool again". It carries `connect_instructions_url` (`GET /api/v1/mcp/connect`) under a name that says what it IS — a machine-readable document, not a page. The field was called `login_url` until a human opened it in a browser and got raw JSON: connecting happens INSIDE the client and no web page can do it, so the text names the real step (`/mcp → Authenticate`, or `claude mcp login <server>` in a terminal of its own, which it needs). Building the link with `start_login` instead would hand an anonymous caller a generator of login sessions. `keyless_alternative` is true PER TOOL: for a `SESSION_TOOLS` member it offers the `start_login` + `wait_for_login` road, and for every other keyed tool it says that road will NOT open this tool and names what a session does cover — offering it unconditionally sent a signed-in caller to a second refusal that contradicted the first. That enumeration of the session surface exists FOUR times (here, `wait_for_login`'s description, `HttpClient`'s own `api_key_required` — the second refusal — and `serverInstructions`) and is pinned equal across all four by `__tests__/tools.test.ts`. **Also the two channels a client delivers anonymously and ALWAYS**, added because the 401 above never reaches the model: an MCP client raises it as a TRANSPORT error and throws before the body becomes a tool result, so a live Claude Code session filled the gap with its own guess — "the token expired", about a server never handed a token. `accessNoticeFor(tool, ctx)` returns the suffix `factory.ts` appends to a description — empty when a credential is present or the tool is keyless, otherwise one text for `SESSION_TOOLS` and another for keyed tools, each naming the transport's recipe and ending in "call this tool again" (the half the 401 body states twice over for the worst measured client). `serverInstructions(ctx)` is the `initialize` string: it DERIVES the keyless list from `KEYLESS_TOOLS` rather than restating it, says the granted key's SCOPES decide which tools work (the default grant is five, so "opens every tool" would be a pre-written 403), and names the transport's own opaque-failure causes. Cost, measured on the built server: the notice adds ~22 KB to ~42 KB of descriptions across the 166 non-keyless tools, and a keyed server pays none of it. `__tests__/auth-boundary.test.ts` compares the keyless list against the tools the factory actually registers, in BOTH directions, without calling any of them, and holds `SESSION_TOOLS` to registered names disjoint from `KEYLESS_TOOLS`.
- `src/remote.ts` - Streamable HTTP entry point (`h-mcp-remote`), deployed as its own service. One `createProofServer()` PER CONNECTION — `HttpClient` keeps `sessionToken` AND now the connection's API key on the instance, so a shared client would hand the next user the previous user's login or key. **ANONYMOUS FIRST, KEYED ON REQUEST** (`h-mcp-oauth-remote-wiring`, replacing the earlier public-mode-only posture): a client that has been through the OAuth ceremony (`h-mcp-oauth-server`) presents its API key in the `Authorization` header, and that is the ONLY place a credential is read — `?api_key=` never is (a token in a URL lands in proxy logs and `Referer`; pinned behaviourally by the SC-8 block in `__tests__/remote.test.ts`, confirmed by mutation). The token is resolved ONCE, at open, through the existing self-inspection `GET /api/v1/me/api-key` — purely so the refusal is legible (dead token → 401 + challenge, so a client refreshes; missing `settings:read` → 403 naming the scope; API unreachable → 503). Nothing is cached from it: the key travels to the backend on every call, so `DELETE /me/api-keys/:id` takes effect on the NEXT call rather than at session TTL, and every scope decision stays in `requireScopeIfApiKey`. A session also carries the SHA-256 of the credential that opened it, so a leaked `mcp-session-id` cannot spend somebody else's key and a request that drops the header is refused — on the KEY road. **Stated bound**: a session that opened anonymously and then signed in from inside (`start_login`) has no credential of its own to bind to, so there the `mcp-session-id` is itself the credential (bounded by it being a `randomUUID` and by the session TTL). **There are TWO ways for a session to have an account, and the gate reads both**: the presented API key, and a login performed from INSIDE the session (`start_login` / `wait_for_login` → `captureSetCookie` holds a live JWT on this connection's client, and the `SESSION_AUTH_PREFIXES` tools travel with it). Reading only the first closed the one road a client without OAuth has to a key — the user signed in and was told to sign in — while the refusal text was still advertising exactly that road. The self-inspection runs on its OWN client (`maxRetries: 0`, 5s) rather than the session's: it happens inside the capacity reservation, and the ordinary client's retries plus a `Retry-After: 60` from the backend's shared per-pod `/me` bucket turned one credential-less request into a 120-second hold on a session slot (measured, with a legitimate anonymous open answered 503). It also carries a LOCAL token budget (`createResolveBudget`, exported for its own test: 1/s sustained, burst = `min(maxSessions, RESOLVE_BURST_CEILING)`, monotonic clock with the elapsed clamped at both ends, `429` + `Retry-After` when spent): the refusal path releases its slot at once, so nothing else bounds how fast bearer-carrying opens arrive, and the backend's `/me` bucket is ~5 r/s keyed on the pod's egress IP and shared by every tenant AND by every ordinary `/me/*` tool call — one source inside the proxy's own 30 r/s limit would drain it and answer 429 to every LEGITIMATE sign-in while the anonymous surface kept working and the service looked healthy. The burst follows the session cap — a reconnect herd after a restart is bounded by how many sessions a replica holds, and the SDK client does not retry a 429 — but is CLAMPED by `RESOLVE_BURST_CEILING` (100), because the cap is per replica while the bucket it spends is fleet-wide: `src/__tests__/drift/mcp-remote-deployment.test.ts` derives `replicas × min(MCP_MAX_SESSIONS, ceiling)` — the EFFECTIVE burst — against the backend's own `ipRateLimit(300, 60, 'me')` literal and goes red before the fleet burst could take the whole minute's allowance; raising the CEILING itself is held by the unit case in `mcp/__tests__/remote.test.ts` that runs a cap above it, since while the manifest cap sits at or below the ceiling the drift figure cannot see the ceiling move. Raising `MCP_MAX_SESSIONS` past the ceiling therefore does NOT raise the burst. A SECOND and unrelated clamp sits inside `take()` — the elapsed is floored at zero — and that one exists for the clock: a backwards wall-clock step drove the unclamped bucket to −7190 tokens and refused every keyed connection for about an hour (measured). The two are independent, and fixing the clock is not a reason to drop the ceiling. **Stated residual**: the bucket is keyed on nothing, so a source sending garbage bearers above the refill rate keeps new keyed connections refused — strictly better than spending the shared backend bucket, but not nothing; keying per client IP needs a decision about trusting `X-Forwarded-For` that this task did not take. The `api_key_required` text is transport-aware (`HttpClientConfig.remote`): the stdio instruction ("put it in `PROOF_API_KEY` and restart") is impossible on a server somebody else runs, and after the gate learned to accept a logged-in session that text is exactly what a signed-in remote user reaches outside the session surface. **An ANONYMOUS handshake asking for nothing keyed is never refused**: with no credential presented, the 401 lands on the tool call and never on a bare `initialize` or `tools/list` — the control measurement for the alternative reached the human as `Failed to connect — connection timed out after 30000ms`, i.e. no connection at all (`docs/mcp-oauth-client-probe.md`). Three cases DO answer 401 at the handshake: a PRESENTED token that does not resolve (so the client refreshes), a request whose credential does not match the session it names, and an opening BATCH that smuggles a keyed `tools/call` next to `initialize` — the last one is anonymous, and is refused because the tool call in it is what asks for an account. A refusal is not work: it releases the in-flight slot and does not move the idle clock. Session ids are minted `<replica>.<uuid>` and the proxy routes on that prefix; hashing the id cannot work, because the replica is chosen before any id exists (measured: 45 of 60 follow-ups landed on a replica that had never heard of the session). **Bounds, each because the unbounded version was measured failing:** sessions are RESERVED before the first `await` (`MCP_MAX_SESSIONS`, default 100 — a check against `sessions.size` alone admitted 25 concurrent opens against a cap of 2, because the map is written several awaits later); request bodies are capped at 4MB (one 256MB body took the process to 859MB RSS against a 768Mi limit); the sweeper skips sessions with a POST in flight (`MCP_SESSION_TTL_MS`, default 30min — a `lastSeen` stamp alone closed the transport under a call that outlived the TTL, and `wait_for_*` polls for minutes by design). POST only, deliberately: `handleRequest` for a standalone `GET /mcp` stream resolves only when the stream ends, and the SDK client opens one right after `initialize`, so counting it made the documented TTL unreachable for every real session (measured: one survived 6× its TTL); and nothing is constructed for a POST that is not an `initialize`. `/healthz` reports the live session count. **The image builds from the REPOSITORY ROOT** (`docker build -f mcp/Dockerfile .`) until `@proof-holdings/delegation-verifier` is published — from `mcp/` alone `npm ci` 404s on it. **Deployment manifests live in `k8s/mcp-remote/` and are deliberately NOT in `k8s/base`**: nginx resolves upstream names at config-parse time and `[emerg]`s on a miss, so an upstream pointing at a not-yet-deployed pod would stop the whole production ingress; see that directory's README.
- `probe/anon-connect-probe.mjs` - The SC-1 measurement, not part of the server: a bare Streamable HTTP server with zero auth middleware used to answer "does a real client connect anonymously?" (it does — three clients, `docs/mcp-remote-anon-probe.md`). Pinned by `src/__tests__/drift/mcp-remote-probe.test.ts`.
- `probe/oauth-probe.mjs` - The second measurement (`h-mcp-oauth-probe`), same shape and same rule — zero imports from `@modelcontextprotocol/sdk/server/auth/*`, so a failure cannot be ambiguous between "the client cannot do this" and "our server is broken". One `node:http` process serving BOTH the resource (`/mcp`, tools `probe_echo` = keyless and `probe_whoami` = answers 401 with `WWW-Authenticate`) and a toy authorization server (`/authorize`, `/token`, `/register`, `/revoke`, metadata documents). Flags select the measurement: `--mode always-401` (the control — 401 on `initialize` itself), `--no-dcr` (no `registration_endpoint`, `/register` 404), `--omit-field <name>` (prove a metadata field is mandatory by removing it and re-running). Every inbound request is logged BEFORE routing, 404s included, which is what makes "the client never asked for that document" an observation. Verdict in `docs/mcp-oauth-client-probe.md`; pinned by `src/__tests__/drift/mcp-oauth-probe.test.ts` (hash↔report, no auth imports, logging-before-routing, plus the measured SHAPE behaviourally — a hash mismatch is repaired by re-citing the hash, which would otherwise leave the verdict standing over a probe that stopped measuring it).
- `probe/instructions-channel-probe.mjs` - The third measurement (`r-mcp-instructions-channel`): does the `instructions` field of an `initialize` response reach model context? Stdio transport, unlike the two HTTP-based probes above — a real MCP client (`claude -p`) connects to it as a local server, not a remote one. An inert canary marker (`INSTRUCTIONS_MARKER`) is set via the `McpServer` constructor option, never written to the private `_instructions` field, so a negative result couldn't be confused between "the channel is dead" and "our own write mechanism failed". 5/5 live sessions reproduced it verbatim and none treated it as an instruction to act on. Verdict in `docs/mcp-instructions-channel-probe.md`; pinned by `src/__tests__/drift/mcp-instructions-probe.test.ts` (no `_instructions` property access, no imports from `packages/delegation-self-refusal` or `mcp/src`, hash↔report, marker constant↔report, plus the measured SHAPE — spawns the probe for real and confirms `initialize` actually returns the marker, not just that the source text contains it).
- `src/http.ts` - HTTP client with API-key `Bearer` auth, retry (429/5xx/timeout, exp backoff capped 10s), `ApiError`. **Public mode** (`h-mcp-public-mode`): `apiKey` is optional, the `Authorization` header is CONDITIONAL (the key is absent from the object, never present as `Bearer undefined` — a well-formed credential the backend would try to resolve), and a call with no bearer to a path outside `PUBLIC_PATHS` throws `api_key_required` BEFORE `fetch`, so an agent gets "there is no key yet" rather than a round trip ending in `invalid_token`. `PUBLIC_PATHS` holds (method, prefix) PAIRS, not bare prefixes: `/api/v1/auth/sessions` is shared by two public routes and by `GET /auth/sessions` + `DELETE /auth/sessions/:id`, which need a key. Drift-guarded by `parseMcpPublicPaths` (`scripts/api-map-shared.ts`) plus `validateMcpPublicPathCoverage` and its mirror in the backend `api-parity` test — that rule is a LOWER BOUND (it demands the 4 `auth: public` + `mcp: available` endpoints), and a separate case pins the list as a STRICT SUPERSET, because the two poll routes it also carries are held `planned` in the map and a "cleanup" down to the rule would break both `wait_for_*` tools with every check still green. `del()` accepts an optional body (authorizations revoke). **JWT session auth**: `captureSetCookie()` transparently reads the `token`/`refresh_token` cookies the login flows set. On the **pure-`jwtAuth`** surface only — `SESSION_AUTH_PREFIXES` (`/me/{emails,phones,api-keys,2fa,domains,dns-credentials,dns-providers,verification-requests,verify/,account}` plus the jwt-only `/profiles/me/{username,proofs}`) plus exact `/api/v1/auth/me` — the client sends `Authorization: Bearer <JWT>` when a session exists; everything else (incl. the **dual-auth** `/me/{profiles,settings,usage,export,assets}`, `/profiles/me`, `/profiles/me/assets`, `/profiles/profiles/:id/proofs`, `/auth/sessions`) keeps the API key, preserving tenant identity + scope checks. The surface is drift-guarded: `parseMcpSessionAuthPaths` (`scripts/api-map-shared.ts`) text-parses this list, and both `validate-api-map.ts` and the backend `api-parity` drift test require every `auth: jwt` endpoint claimed `mcp: available` to be covered by it (a jwt tool outside the surface would always fail `invalid_token`). On `401 token_expired` it auto-refreshes once via `POST /auth/refresh` (single in-flight `refreshing` promise so a single-use refresh token is spent once) and retries; a failed refresh clears the session and propagates the 401.
- `src/types.ts` - `ToolRegistrar` alias, `credentialsSchema` (DNS creds: values ≤2000 chars, ≤20 keys), the canonical `VERIFICATION_TYPE_VALUES` (7 asset types) + `VERIFICATION_CHANNEL_VALUES` (21 channels) enums (single MCP source, kept in lockstep with backend `src/middleware/validate.ts` `verificationTypeSchema`/`verificationChannelSchema` — comment-guarded, this package can't import backend `src/`), `jsonResult()`/`errorResult()` builders, and `WAIT_DEFAULT_SECONDS` — the ONE default every `wait_for_*` tool falls back to, deliberately under the MCP SDK's 60 s `DEFAULT_REQUEST_TIMEOUT_MSEC`: this server sends no progress notification, so a longer wait is cut off by the CLIENT while the server is still polling (`MCP error -32001`, measured live against the old 120 s default while a human was scanning a QR code). The 10-minute figure in `docs/POLLING_CONTRACT.md` is for SDK waits that own their own clock; a tool call does not.

### Tool Modules (`src/tools/`)
Organized by resource; each module's tool count + notable specifics:
- `verifications.ts` (14) — incl. multi-channel create/status (one phone × up to 4 unique channels, first-wins, one proof token, quota charged per channel).
- `proofs.ts` (4) — `get_proof_status` and `revoke_proof` both take a PUBLIC handle (`ph_ctl_*`/`ph_dlg_*`) or a verification id, and their descriptions carry the two facts an agent must not get wrong: a live proof reads `active` (not `verified`), and revoking a proof is terminal but does NOT withdraw the asset, consent or delegation it is about.
- `verification-requests.ts` (7), `templates.ts` (7), `webhook-deliveries.ts` (4), `assets.ts` (3), `sessions.ts` (3), `billing.ts` (1), `auth.ts` (3), `emails.ts` (7), `phones.ts` (5), `domains.ts` (17), `dns-credentials.ts` (3), `user-requests.ts` (7), `user-domain-verify.ts` (3), `public-profiles.ts` (2), `authorizations.ts` (5, revoke is DELETE-with-optional-body).
- `settings.ts` (8) — incl. `get_platform_summary` (`GET /me/summary` one-call snapshot; `hitl_channels` needs `hitl:read`), `search` (prefix-anchored global account search, 6 buckets, recipient identifiers masked), and the two per-key endpoints (`get_self_api_key` requires API-key auth → 400 `api_key_required` for JWT; `get_api_key_usage` counts-only, own-key-only).
- `profiles.ts` (14).
- `api-keys.ts` (4) — `create_api_key`'s `scopes` enum (`validScopes`) mirrors the backend canonical taxonomy in `src/constants/apiKeyScopes.ts` (all 13 resource groups); this package can't import backend `src/`, so it's kept in lockstep by the backend drift test `src/__tests__/drift/api-key-scopes.test.ts`. Also accepts an optional `profile_id` (24-hex) binding the key to a sub-account project — immutable, backend-validated for ownership.
- `twofa.ts` (5), `hitl.ts` (9), `hitl-keys.ts` (3).
- `delegations.ts` (4) — Proof of Delegation lifecycle: `create_delegation`/`list_delegations`/`get_delegation`/`revoke_delegation` against `/api/v1/delegations*` (id accepts Mongo id or `ph_dlg_*` handle; list never includes tokens). `list_delegations`' description and its `status` param both state the split an agent must not get wrong: every item carries a DERIVED `effective_status`/`is_valid` (both lifetimes — the control proof's and the delegation's own, `expired` once either has passed; the value to act on), while `status` and the `status` FILTER are the delegation's own revocation record.
- `delegation-verify.ts` (2) — checks (not publishes) delegations, no API key: `verify_delegation` (one artifact) and `verify_delegations` (up to 50, `h-proof-checker-mcp`) both run `@proof-holdings/delegation-verifier` against the issuer's public surfaces only. Both require `delegate` (the artifact identity the CALLER resolved) and `expected_principal` (the domain the caller expects), never read off the card being checked — a published token is a bearer artifact anyone can paste into another card. `verify_delegation`'s failure JSON carries the package's own `outcome: 'invalid' | 'unconfirmed'` straight through (`h-delegation-verifier-status-fallthrough-gate`), so a `status_unavailable` result is structurally distinguishable from a `revoked` one, not just by the `reason` string. `verify_delegations` factors its per-item core out of `verify_delegation` (`verifyOneDelegation`), always checks revocation (no `check_status` skip), and buckets every failure into its own richer `confirmed_invalid | no_claim_found | unconfirmed` via `delegation-verify-outcomes.ts`'s `FAILURE_REASON_OUTCOME` map — DERIVED from the package's binary `outcome` for every reason except four explicit local overrides (`no_publication` → `no_claim_found`, `multiple_publications`/`invalid_options`/`no_trust_policy` → `unconfirmed`, where this tool's three-bucket vocabulary reads differently than the binary split would by default), still exhaustive over the verifier's `FailureReason` union at compile time via `Record<>` and at runtime via a test that text-scans the union — an unreachable issuer lands in `unconfirmed`, never `confirmed_invalid`. Neither tool discovers installed artifacts or fetches a caller-supplied URL: both verify material the caller already holds (`card`/`token`), the same trust boundary `src/services/delegationPointer/resolve.ts`'s documented SSRF gaps make deliberate (that hardening is `m-artifact-lookup-surface`'s job, not this one's).
- `proof-me.ts` (7) — anti-impersonation reverse verification: 5 challenger-management tools under `/hitl/:id/challengers*` + 2 identity-challenge tools under `/identity-challenges*`.
- `circles.ts` (13) — Circle people-primitive CRUD (`create_circle`/`list_circles`/`get_circle`/`update_circle`/`delete_circle`) + member management (`add`/`list`/`invite`/`create_..._drill`/`remove_circle_member`) + member-channel management (`add`/`list`/`remove_circle_member_channel`), all API-key-scoped (`circles:create|read|write`); member/channel responses carry presence booleans only (SEC-PM-006, never an identifier).
- `confirmations.ts` (5) — `create_confirmation`'s description explains the v1/v2 envelope choice (on an encrypted config with enrolled approvers, `message` MUST be a v2 multi-recipient ciphertext built via SDK `encryptMessageV2` after `getApproverKeys`, else approvers can't decrypt); no `search` (backend 400s encrypted messages).
- `auth-flows.ts` (2, start/wait login), `accounts.ts` (4) — the agent-bootstrap flow: `create_account` (public, no API key; uniform response = enumeration-oracle protection — and since `h-mcp-public-mode` it DISPATCHES NOTHING on the email channel, answering `email_sent: false` + `send_required: true`), `send_account_email` (the explicit second step that delivers it; its own description tells the agent to confirm with the user first, and `create_account`'s says the mail has not gone out — a drift test pins both, because the description is what an agent reads instead of the schema), `wait_for_account_creation`, `start_2fa_for_action` (optional `ttl_seconds`/`single_use`; MCP enum exposes only the 11 gated scopes; retry flow: sensitive call → 403 `2fa_required` → start 2FA with the returned `action_type` → `render_auth_link` → `wait_for_2fa` → retry).
- `render-auth-link.ts` (1) — LOCAL COMPUTATION (no HTTP): ASCII QR via the `qrcode` package. Exports `registerTools(tool)` with no `http`.

### Tests
- **Unit** (`__tests__/http.test.ts`, `tools.test.ts`) — HttpClient retry/backoff/errors + tool registration/handlers.
- **Description guard** (`__tests__/tool-descriptions.test.ts`) — what the descriptions SAY, which nothing else asserted. Over every registered description AND every `.describe()` hint on its input schema (nested, bounded at depth 3), no SENTENCE may put `qr_text` beside `render_auth_link` or beside the word "URL": `qr_text` is `QRCode.toString(text, {type:'utf8'})` on every producer, i.e. QR art, while `render_auth_link` takes `z.string().url()` — so the pairing instructs something zod rejects, and an agent that obeyed it improvised a PNG the harness refused. Per-SENTENCE rather than per-description because the WARNING that fixes it must name both. Its control is the six verbatim sentences that shipped before the fix, each of which it must fail.
- **Integration** (`__tests__/integration/*`, 22 files) — spawn the real server via `StdioClientTransport` and call each tool against the live API; require `PROOF_API_KEY`/`TEST_API_KEY`, run sequentially, 30s per-test timeout. Helpers: `helpers/mcp-client.ts` (`connectClient`/`callTool`/`parseJsonResult`/`parseErrorResult`), `helpers/test-data.ts` (unique-id generators + sentinels).

### Publishing & Build

## Key Patterns

- **`registerTools(tool, http)`** — every module exports one; tools registered inline with Zod input schemas. `render-auth-link.ts` is the no-`http` exception.
- **Shared schemas/helpers** (`types.ts`) — `credentialsSchema` imported by `domains.ts` + `dns-credentials.ts` + `verifications.ts` (`create_verification.dns_provider`); `VERIFICATION_TYPE_VALUES`/`VERIFICATION_CHANNEL_VALUES` consumed by `verifications.ts` + `verification-requests.ts`; `domains.ts` also holds `dnsProviderSchema` + `EMAIL_PREFIXES`.
- **`pollUntilTerminal`** — shared polling helper for every `wait_for_*` tool (exp backoff 2s→30s + jitter, 2× emergency backoff on 429/5xx). Each individual poll is raced against the REMAINING budget, so a request that hangs cannot carry the call past its own timeout and into the client's — the budget used to bound only when a new iteration may START, leaving the last fetch bounded by `HttpClient`'s own 30 s. Running out of time is NOT an error: it answers a non-error `status: "pending"` carrying the resource's own `last_status`, the elapsed `waited_seconds` and the `timeout_seconds` it was given. An `isError` "Timeout" made agents report a login as failed while the human was still scanning the QR. That makes each tool's TERMINAL-STATE list load-bearing in a new way — a state missing from one turns "not yet, call again" into a permanent instruction on a resource that will never move — so `__tests__/tools.test.ts` derives the states from the array each tool passes and requires its description to name every one, and pins the wait-tool set to the DIRECTORY with exactly one `pollUntilTerminal(` per file.
- **Verification enums** — `verifications.ts` (`create_verification`: `type`+`channel`+`identifier`, mirroring the REST `createVerificationSchema`) and `verification-requests.ts` both build their `z.enum`s from the shared `types.ts` constants; `list_verification_requests` `status` = the 5 persisted statuses + the synthetic `active` alias (server-side time-aware).
- **Error handling** — handlers catch `ApiError` and return `errorResult()` (`isError:true`) rather than throwing (the MCP protocol always gets a structured response); non-API errors re-thrown. Results JSON-serialized via `jsonResult()` (MCP `type:'text'` content blocks).

## Configuration

### Environment Variables
- `PROOF_API_KEY` (OPTIONAL since `h-mcp-public-mode`) — API key (Bearer). Absent → public mode (see Purpose above); the server logs a notice and starts. Both published cards say so: `server.json` carries `isRequired: false` and `smithery.yaml` no longer lists `apiKey` under `required` — each is pinned by its own assertion in the backend `src/__tests__/drift/delegation-publication.test.ts`, since the pre-existing card check read variable NAMES only and stayed green on a card claiming the key was mandatory.
- `TEST_API_KEY` (optional) — alternative key for integration tests.
- `PROOF_BASE_URL` (optional) — API base URL (default `https://api.proof.holdings`).

### HttpClient Defaults
Timeout 30s, max 2 retries (3 attempts), exp backoff capped 10s. Retries on 429 (respects `Retry-After`), 5xx, timeouts.
